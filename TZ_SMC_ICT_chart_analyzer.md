# ТЗ: AI-агент для анализа графиков по методологии Smart Money Concept (SMC/ICT)

## 1. Цель проекта

Разработать систему, которая:
- получает рыночные данные (BTCUSDT, EURUSD, DXY и др.) в разных таймфреймах;
- строит график (аналог TradingView) программно;
- с помощью локальной мультимодальной модели (VLM) и текстовой базы знаний (структурированные конспекты лекций по SMC/ICT) размечает на графике order block, fair value gap, swing high/low, liquidity sweep, BOS/CHoCH и т.д.;
- применяет логику сессий (Asian/London/New York) и дней недели ("если понедельник сделал X, то вторник должен сделать Y");
- учитывает календарь новостей (NFP, CPI, FOMC) и корректирует прогноз/сценарий на неделю;
- выдаёт структурированный итог: bias (bullish/bearish), ключевые уровни (POI), сценарий, уверенность.

## 2. Архитектура (высокоуровнево)

```
[Market Data Source] → [Data Pipeline] → [Chart Renderer] ─┐
                                                             ├→ [Orchestrator] → [VLM/LLM] → [Structured Output]
[Lecture Notes] → [Knowledge Base (RAG)] ──────────────────┤
                                                             │
[Rules Engine: Sessions/Days/News] ─────────────────────────┘
```

Ключевая идея: **не полагаться только на VLM для точных ценовых уровней**. VLM хорошо интерпретирует и объясняет, но плохо определяет точные координаты паттернов на изображении. Поэтому order block/FVG/swing high/low детектируются алгоритмически (по OHLCV, не по картинке), а VLM получает и картинку, и уже размеченные алгоритмом зоны — и работает как "аналитик", а не как "детектор пикселей".

## 3. Этапы разработки

### Этап 0. Фиксация scope и технических ограничений
- Определить итоговый список инструментов (BTCUSDT, EURUSD, DXY, +резерв).
- Определить таймфреймы анализа (например: недельный контекст → дневной → 4h → 1h → 15m).
- Зафиксировать локальную модель (VLM) и железо (VRAM), это влияет на выбор модели.
- Зафиксировать источники данных (см. Этап 1) — легальные, с API, без нарушения ToS TradingView.
- **Definition of Done:** документ с зафиксированными parameters (инструменты, TF, модель, источники данных).

### Этап 1. Data pipeline (получение рыночных данных)
- Крипто (BTCUSDT и т.п.): `ccxt` + Binance/Bybit API — историчные и realtime OHLCV.
- Форекс/DXY: TradingView не даёт официального API для скрапинга (нарушение ToS). Использовать легальный провайдер: Twelve Data, Alpha Vantage, OANDA API, Polygon.io, или брокерский MT5/MT4 API.
- Нормализовать все данные в единый формат: `timestamp, open, high, low, close, volume`.
- Хранение: SQLite/PostgreSQL или Parquet-файлы для истории.
- **Definition of Done:** скрипт получает OHLCV по любому инструменту/TF и сохраняет в единую схему.

### Этап 2. Chart renderer (построение графика)
- Генерация свечного графика в PNG/SVG на основе OHLCV: `mplfinance`, `lightweight-charts-python` или `plotly` + headless-рендер (playwright/kaleido).
- Настраиваемые параметры: таймфрейм, глубина истории, разметка сессий (вертикальные зоны Asian/London/NY на графике).
- **Definition of Done:** по запросу (symbol, TF, N свечей) генерируется изображение графика, идентичное по смыслу TradingView.

### Этап 3. Алгоритмический SMC-детектор (без LLM)
Это ядро точности системы — реализовать rule-based на Python поверх OHLCV:
- **Swing High / Swing Low** — локальные экстремумы (fractals).
- **BOS / CHoCH** — пробой структуры.
- **Order Block** — последняя противоположная свеча перед импульсным движением.
- **Fair Value Gap (FVG)** — imbalance между свечами (gap между high[i-1] и low[i+1]).
- **Liquidity sweep** — прокол экстремума с возвратом.
- Вывод: структурированный JSON с координатами/ценами всех найденных зон по каждому инструменту/TF.
- **Definition of Done:** на исторических данных детектор находит паттерны, которые можно визуально сверить с ручной разметкой на TradingView (self-check на 20–30 примерах).

### Этап 4. База знаний (RAG) из лекционных материалов
- Взять структурированные конспекты (сессии, дневные/недельные паттерны, правила по новостям).
- Разбить на смысловые чанки (по темам: "правила азиатской сессии", "правила недели", "правила NFP" и т.д.).
- Векторизация (например, `bge-m3` или `nomic-embed-text`) + локальная векторная БД (Chroma/Qdrant).
- **Definition of Done:** по запросу ("что означает манипуляция Лондонской сессии после определённого паттерна Asian range") система возвращает релевантный чанк.

### Этап 5. Rules Engine: сессии, дни недели, новости
- Формализовать правила из лекций в конфиг (YAML/JSON), например:
  - `if Asian_session == "range" and London_session == "manipulation_up" → expected: NY_reversal_down`
  - `if Monday == "expansion" → Tuesday: "consolidation"` (и т.д., по вашей методологии).
- Отдельный модуль-трекер: определяет, что фактически произошло в каждой сессии/дне (на основе Этапа 3), и сверяет с ожиданиями по правилам.
- Интеграция экономического календаря: NFP/CPI/FOMC — через API (Trading Economics, Financial Modeling Prep; ForexFactory скрапить нельзя — ToS). При наличии события — применяется отдельный набор правил (например, "не торговать до/после X минут", "ожидать expansion").
- **Definition of Done:** модуль на вход получает дату/неделю → на выход даёт список активных правил и их статус (сработало/не сработало/ожидается).

### Этап 6. Оркестратор (сборка контекста для VLM)
- Формирует единый запрос к локальной VLM, включающий:
  1. изображение графика (Этап 2),
  2. JSON с алгоритмически найденными паттернами (Этап 3),
  3. релевантные чанки базы знаний (Этап 4),
  4. статус правил сессий/дней/новостей (Этап 5).
- Промпт просит модель не "искать" паттерны с нуля, а **интерпретировать уже размеченные данные** и сформировать нарратив/сценарий.
- **Definition of Done:** оркестратор собирает полный промпт и получает осмысленный ответ от локальной VLM на тестовом примере.

### Этап 7. Структурированный вывод
- Зафиксировать JSON-схему ответа модели: `bias`, `key_levels (POI)`, `narrative`, `session_status`, `active_news_risk`, `confidence`.
- Заставить модель отвечать строго в этом формате (function calling / constrained JSON, если поддерживается локальным сервером — например, через Ollama/vLLM с grammar-режимом).
- **Definition of Done:** ответ всегда парсится в валидный JSON без ручной коррекции.

### Этап 8. Backtesting / валидация
- Прогон системы по историческим неделям: сравнить сгенерированный сценарий с тем, что реально произошло.
- Логировать расхождения — они используются для доработки правил (Этап 5) и промптов (Этап 6).
- Метрики: % совпадения bias, % отработки ключевых уровней.
- **Definition of Done:** отчёт по N исторических недель с метриками точности.

### Этап 9. UI / доставка результата
- Вариант A: простой веб-дашборд (Streamlit/Next.js) — график + разметка + нарратив.
- Вариант B: Telegram-бот — присылает анализ по расписанию (например, перед открытием Лондонской сессии).
- **Definition of Done:** пользователь получает готовый анализ без ручного запуска скриптов.

### Этап 10. Мониторинг и итеративное улучшение
- Логирование всех промптов/ответов.
- Механизм обратной связи (пользователь отмечает, было ли предсказание верным) → используется для донастройки Rules Engine.
- **Definition of Done:** налажен цикл сбор данных → анализ ошибок → корректировка правил.

## 4. Рекомендуемый стек
- **Backend:** Python, FastAPI
- **Данные:** ccxt (крипто), Twelve Data/OANDA (форекс/DXY), pandas
- **График:** mplfinance / lightweight-charts-python / plotly+kaleido
- **VLM:** Qwen2-VL, LLaVA-NeXT или InternVL2 (через Ollama/vLLM/LM Studio — в зависимости от VRAM)
- **RAG:** Chroma/Qdrant + bge-m3/nomic-embed
- **Оркестрация:** LangChain/LlamaIndex или собственный слой без фреймворка
- **Хранение:** PostgreSQL/SQLite
- **Календарь новостей:** Trading Economics API / Financial Modeling Prep
- **Деплой:** Docker-compose (все компоненты локально)

## 5. Ключевые риски
- VLM ненадёжна в определении точных ценовых координат по картинке → решается гибридным подходом (Этап 3 обязателен, не опционален).
- TradingView не предоставляет официальный API для получения данных таким способом — использовать легальные источники, иначе риск блокировки/нарушения ToS.
- Методология SMC/ICT частично дискреционная — даже идеальный алгоритм не даст 100% совпадения с "ручной" разметкой трейдера; нужен этап калибровки правил на реальных данных (Этап 8).
- Ограничение по VRAM локальной модели определяет, какую VLM реально можно использовать в реальном времени.

## 6. Порядок работы для AI-агента
Этапы 0→10 предполагается проходить последовательно, но Этап 3 (алгоритмический детектор) и Этап 4 (база знаний) можно разрабатывать параллельно, так как не зависят друг от друга. Каждый этап должен заканчиваться проверяемым Definition of Done перед переходом к следующему.
